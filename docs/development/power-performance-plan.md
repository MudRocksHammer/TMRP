# 受信サーバーの性能試験計画

2026-10-29。対象はMQTT → 検証 → PostgreSQL COMMIT → ACKの受信サーバー。
台帳の12電力メーター × 1 Hz = **12件/秒**を現在の基準負荷とする。
334件/秒は将来増設の探索条件、1,000件/秒はストレス条件であり、実設備の確定要求ではない。
デスクトップ配信・履歴API・操作APIは未実装のため、その性能を合格とは判定しない。

以下の時間・容量の閾値は、このプロジェクトの**暫定受入目標**。
法令・業界規格・安全制御の認証基準ではなく、実機頻度・運用SLAの決定後に更新する。
計測が間に合わない、送信予定数を生成できない、サンプルが欠ける試験は合格にしない。

## 合格基準

- 正常な一意メッセージの欠損、意図しない追加行、内容の変更、二重保存：0件。
- 重複入力はduplicate、同じ識別子の異なる内容はconflict、不正入力はrejectedとして照合する。
- 通常・余裕負荷：予定送信時刻からコミット後ログまでp95 ≤ 500 ms、p99 ≤ 1,000 ms。
- 送信器の予定に対する遅れp99 ≤ 100 ms。これを超えたら負荷生成が不成立で、受信性能の合格には使わない。
- 定常負荷中のreadiness失敗・処理エラー：0。受信プロセス平均CPU < 1コアの70%、RSS < 256 MiB。
- 集中送信・停止復旧：送信完了／再起動開始から30秒以内に全件処理。停止中の遅延を通常SLOと比較しない。
- 継続運転：今回の短時間試験では開始約10秒後からRSS増加 ≤ 10 MiB。本番の長時間試験は別基準を適用する。
- BrokerのPUBACK成功だけでは保存成功としない。DB全行の識別子とJSONB本文、拒否理由別件数を照合する。

## 今回自動実行する条件

各ケースは新規スキーマ・新規受信プロセスで実行し、初期の冷えた状態も測定に含める。
全ケースで12本の送信接続、QoS 1、retain=false、実際のJSONログを有効にする。

| 試験 | 入力条件 | 合格基準・目的 |
|---|---|---|
| baseline | 12件/秒 × 30秒 = 360件 | 基準負荷で上記の全基準を満たす |
| headroom | 120件/秒 × 30秒 = 3,600件 | 10倍の余裕を確認。通常の遅延・資源基準を適用 |
| growth | 334件/秒 × 30秒 = 10,020件 | 将来負荷の探索。同じ基準で評価するが、初版リリースの必須容量とはしない |
| stress | 1,000件/秒 × 30秒 = 30,000件 | 限界の兆候を探す。失敗した閾値を報告し、合格負荷へ読み替えない |
| burst | 3,600件を2秒以内に投入 | 30秒以内の排出、完全性、RSS。通常の遅延閾値は対象外 |
| soak | 12件/秒 × 120秒 = 1,440件 | 短時間の継続運転、メモリ増加。24時間試験の代替ではない |
| mixed | 120件/秒 × 30秒。正常70%、重複10%、衝突10%、不正UTF-8 10% | 正常2,520行、duplicate/conflict/rejected各360件。内容の上書きなし |
| recovery | 購読成立後に受信器のみ停止し、約10秒で120件送信して再起動 | Brokerが稼働したままの永続セッションによる全件再配送、再起動開始から30秒以内 |
| large_payload | 120件/秒 × 30秒、本文16,384 bytes | 許容上限サイズで通常の遅延・資源基準。JSON末尾の空白でサイズを調整 |

既存の結合テストも別途実行する：COMMIT失敗時の未ACK、DB制約による保存失敗後の再配送、ACK失敗後の重複処理、Broker再起動と再接続、順序逆転、異なるboot_id。
これは障害時の機能検証であり、高負荷中の復旧時間測定とは区別する。

## 計測方法と限界

実行器は[scripts/benchmark/power_receiver.py](../../scripts/benchmark/power_receiver.py)。
既存のsimulate_power.pyは1件のPUBACKを待つため、性能測定では使用しない。
試験器は受信側やPUBACKを待たずに、単調時計で定めた送信予定に沿って投入する。
送信遅れも記録し、負荷を発生させられなかったケースを検出する。

- 主遅延：**予定送信時刻 → telemetry_processedログ時刻**。Broker待機、送信器の遅れ、検証、DB処理を含む。
- 補助遅延：publish呼び出し直前 → 同ログ、handlerのelapsed_ms。
- 結果ログはCOMMITとACK API要求の後に生成される。厳密なCOMMIT時刻ではなく、保存完了までの遅延の上限側の代理値。BrokerがACKを受信した時刻ではない。
- event_timeやreceived_atを保存完了時刻として使わない。同一ホストの壁時計を使うため、時計の急変がない前提。最終版の実行器は開始から終了までの壁時計と単調時計の差が50msを超えると失格にする。往復する時計ジャンプまでは検出できない。別ホストでは時刻同期誤差も測定する。
- 分位点はnearest-rank。遅延集計対象は新規保存の全メッセージ。重複・不正・衝突は件数照合とhandler時間で検証する。
- 0.5秒ごとにreadiness、処理件数、/procのCPU・RSSを採取。瞬間的なピークやサンプル間のreadiness失敗は捉えきれない。
- CPUは1コアを100%としたプロセスCPU。DBバックエンド値はcheckpointer/WAL writer等を含まない。ホスト全体・ディスクの専用計測は本番候補環境で追加する。
- observed_pending = 投入済み − health処理済み。試験器・Broker・処理中を含む概算で、Brokerの実キュー長ではない。
- ログはファイルへ出力する。journald・転送エージェント・ログローテーションの性能は未検証。
- 各ケース1回、DBは空から開始。大量の履歴があるDB、長時間のcheckpoint、他処理との競合、ネットワーク越しの容量保証には使わない。
- 12接続で高頻度化する試験であり、334台／1,000台の同時接続試験ではない。

## 安全な分離と再実行

ランダムな`perf_power_<uuid>`スキーマ、127.0.0.1の空きポートの一時Broker・受信器のみを作成する。
終了時は自分が作成したプロセスを止め、そのスキーマのみを削除する。既存スキーマ・Broker・サービスを操作しない。
DB自体は共有されるためCPU・ディスクI/Oは競合する。本番DBへこのローカル試験器を向けない。
Brokerはメモリ保持、キュー上限100,000件／128 MiB、本文パケット上限32 KiB。
永続化なしなのでBroker停止を伴うデータ耐久性はこの試験では測定しない。

Linux、Mosquitto、プロジェクトの仮想環境、テスト用PostgreSQLのスキーマ作成権限が必要。
結果フォルダが存在すると停止するので、再実行時は別名にする。

```bash
# TMRPのルートへ移動する
cd /home/shou/pythonLearning/TMRP
# 試験用DBを指定する。接続情報はレポートへ書き込まれない
export TMRP_TEST_DSN='host=/var/run/postgresql dbname=tmrp_dev user=shou'
# 9ケースを実行し、集計JSON・各ケース結果・0.5秒ごとのCSV・生ログを保存する
PYTHONPATH=src .venv/bin/python scripts/benchmark/power_receiver.py \
  --output reports/power-performance-YYYYMMDD-run2
# 例：基準負荷だけを10秒で再実行する
PYTHONPATH=src .venv/bin/python scripts/benchmark/power_receiver.py \
  --scenario baseline --duration 10 --output /tmp/tmrp-performance-smoke-new
# 受信障害の機能テストと全回帰テストを実行する
.venv/bin/python -m pytest -q
```

全合格は終了コード0、閾値不達・ケース実行エラーは1、引数不備は2。
設定ファイルやsamples.csvも結果フォルダに保存する。生ログはGitの既存ルールで除外される。
自動試験は1ケース最大100,000件。長時間本番試験は別の負荷基盤と監視基盤で行う。

## 本番候補環境で追加する試験

未実行の項目を合格として扱わない。各負荷はウォームアップ10分後に最低3回測定し、最悪の回も記録する。
機器頻度・履歴保持日数・同時利用者数・復旧SLAが確定したら下記仮条件を更新する。

| 項目 | 試験条件 | 暫定合格基準 |
|---|---|---|
| 本番経路の定常・余裕負荷 | 実機相当別ホスト送信、MQTT TLS・認証・ACL、DB TLS、実ログ収集、12/120件毎秒を各60分 | 完全性100%、p95 ≤ 500ms・p99 ≤ 1秒、CPU平均70%未満、資源に30%以上の余裕 |
| 長時間運転 | 12件/秒で24時間、120件/秒で2時間、ローテーション・backup・checkpointを含める | 欠損0、通常SLO維持、ウォームアップ後RSSの増加 ≤ 10%かつ持続的右肩上がりなし、FD/スレッドが増え続けない |
| ネットワーク劣化 | 隔離ネットワークでRTT100ms、jitter20ms、損失1%、30秒断を別々に注入 | 接続中p99 ≤ 2秒、復旧後30秒以内に基準負荷へ戻る。Broker保持範囲のデータ欠損0 |
| DB遅延・切断 | 本番相当の隔離DBで100ms遅延、30秒停止、ロック競合、接続上限を注入 | COMMIT前ACKなし、readinessが15秒以内に異常化、DB復旧後60秒以内に再開、再配送の二重保存0 |
| 受信器強制停止 | 120件/秒中にSIGKILL、systemd再起動を10回 | 許容したBroker保持範囲で欠損0、DB一意性維持、各回30秒以内に復旧 |
| Broker再起動・電源断相当 | 永続化・HAを本番設定にして停止、再起動、フェイルオーバー | 合意RPOを満たす。暫定目標RPO=0/RTO≤60秒は未達なら構成見直し。PUBACKだけでディスク耐久性を保証しない |
| キュー飽和・過負荷 | キュー上限を小さくした隔離Brokerで受信停止、定格の2/5/10倍投入 | OOMなし、遅延・滞留・欠損の警報、送信側バッファ／再送規約が機能、負荷解除後60秒以内に回復 |
| 接続数と再接続集中 | 確定台数の1倍・2倍、全機器同時再接続、TLSハンドシェイク | 基準台数は30秒以内に全接続復旧、接続中の通常SLO維持、FD/接続上限の余裕30%以上 |
| 保存期間・ディスク | 30日分相当（12件/秒なら31,104,000行）の履歴、実際の索引と保持削除、容量80%と90% | 通常SLO維持、使用率80%までに警報、枯渇前の対応手順が機能。ライブの共有ディスクを満杯にしない |
| 復元 | 実データ量相当のバックアップから別環境へ復元 | ハッシュ・件数・最新時刻を照合、合意したRPO/RTOを測定。MQTT再配送と復元後重複も照合 |
| 将来の履歴API | 30日分、仮20同時利用者、24時間範囲、ページ最大1,000件、受信120件/秒と並行 | p95 ≤ 1秒、p99 ≤ 2秒、エラー0、受信SLOを悪化させない。API実装後に実施 |
| 将来のデスクトップ配信 | 仮20クライアント、最新状態1 Hz配信、低速・切断クライアント混在 | 保存後の画面反映p95 ≤ 1秒、遅い端末でサーバーのメモリが増え続けない。生全件配信は別要件 |
| 将来の模擬操作 | 仮10同時操作、重複要求・タイムアウト・応答欠損 | 受付p95 ≤ 500ms、重複実行0、状態遷移と監査記録の一致。機器完了時間は機器仕様で別定義 |

DB統計・OS統計の観測箇所は[PostgreSQL公式資料](https://www.postgresql.org/docs/16/monitoring.html)、
MQTTのキュー・永続化条件は[Mosquitto公式設定資料](https://mosquitto.org/man/mosquitto-conf-5.html)を参照。
上記の数値閾値はこれらの資料が規定する値ではない。
