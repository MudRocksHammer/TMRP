# 受信サーバー性能試験結果 — 2026-10-29

**現環境では12件/秒の基本動作を確認できたが、本番性能の受入完了には至っていない。**
120件/秒の全正常入力と最大サイズ入力で暫定遅延目標を超過した。
1,000件/秒・集中送信の試験は負荷生成器が指定条件を満たせず、容量判定には使用できない。

条件と閾値は[性能試験計画](power-performance-plan.md)。既存受信サーバー本体は変更していない。
測定器・判定テスト・この文書を追加した。

## 環境

- ローカルLinux VM、ゲストから見える論理CPU 16、メモリ約3.78 GiB。実行開始時のMemAvailableは約919 MiB。
- Python 3.12.3、PostgreSQL 16.15、Paho MQTT 2.1.0、Psycopg 3.3.6、Loguru 0.7.3。
- fsync / synchronous_commit / full_page_writes はon。共有DB上のランダム専用スキーマを使用。
- Broker・負荷生成器・受信器・DBは同じホスト。12送信接続、QoS 1、平文ループバック通信。
- 通常本文は約496 bytes。受信ログと処理結果ログをJSONでファイルへ出力。
- 他のサービスも稼働する開発環境。専有CPU・専用ディスク・実ネットワーク・本番TLSの保証ではない。

## 初回の9ケース

遅延は予定送信からCOMMIT後ログまで。p95/p99は平均値ではなく、95%/99%のデータが収まる時間。

|---|---|---|---|---|
| 基準負荷 | 12件/秒、30秒、360件 | 360件すべて一致 | 13.7 / 31.1 ms | 合格 |

| ストレス | 1,000件/秒予定、30秒分30,000件 | 期限内に処理完了せず | 容量判定には使用しない | 送信は約301件/秒。試験条件不成立 |

初回は**合格4、遅延基準未達2、負荷条件不成立3**。
試験器の終了コード1はこれらの不合格・不成立を反映する。
機能テストの失敗を表すものではない。

初回の過負荷2ケースでは、DB照合後も停止まで書き込みが進み、DB件数とログ件数の採取時点に差があった。
この2ケースの件数差を損失数として解釈してはならない。
測定器を修正し、受信器を停止してからDBとログの両方を集計するようにした。
また、負荷生成器のin-flight制限を外し、全送信待ち件数の上限10,000件/接続を維持した。

## 負荷生成器の再確認

- 集中送信：3,600件の投入が8.46秒、全件照合一致。処理排出17.65秒。依然として2秒の投入条件を満たさず、判定不能。
- 1,000件/秒の10秒分：10,000件の投入が21.00秒、実効約476件/秒。送信遅れp99約10.96秒で負荷条件不成立。
- 後者は排出待機35秒で打ち切り、停止後のDB・ログとも8,036件で一致、未保存1,964件。残りをその後いつ保存できるかは測定していない。
- 一時Brokerと試験スキーマは測定後に削除するため、この未保存数は**試験終了時の残件**。稼働を続けた場合の恒久損失を証明する値ではない。

基準負荷の再測定では360件すべて一致、p95 13.3ms / p99 17.2msで合格した。
334件/秒の再測定では10,020件を30.00秒で投入できたものの、送信遅れp99が107.8msで100ms基準を僅かに超え、正式には負荷条件不成立となった。
参考値として、排出待機35秒後の停止時点でDB・ログとも8,199件、残り1,821件、保存済み分のp99は約40.04秒。
ほぼ予定の総送信速度でも大きく滞留したが、これを厳密な最大処理能力の値とは扱わない。

## 資源・容量について分かったこと

- 初回受信器RSS最大は約38.4〜38.8 MiB。120秒継続時のRSS増加は約0.13 MiB。長期メモリリークの否定には使えない。
- 初回平均CPUは基準負荷で1コアの約7.2%、120件/秒で約60.7%、上限サイズで約69.2%。全ホストCPU使用率とは異なる。
- 120件/秒の通常データは3,600件で受信ログ約7.46 MB、DB表・索引約3.47 MB。
- 同じデータ・ログ形式で12件/秒を24時間続ける単純外挿では、**ログ約2.15 GB/日、DB表・索引約1.00 GB/日**。
- 30日ならログ約64.5 GB、DB約29.9 GBが目安。小規模試験からの概算で、WAL・バックアップ・bloat・journaldの形式や圧縮・OSログを含まない。

現在のファイルシステムは試験前に空き約21 GiBだった。無期限保存は想定できず、実運用前に保持期間・ローテーション・容量警報を決める必要がある。

## 次に解決すること

1. 別ホストの負荷生成器、またはCベース等の送信器で334/1,000件/秒と2秒の集中送信を確実に成立させる。送信遅れとBroker PUBACKだけでなく、サーバーDB内容を引き続き照合する。
2. 受信器の検証・JSONログ・DB COMMITの時間を分けてプロファイルする。今回の数値だけでは各処理の寄与を断定できない。
3. ログ出力方式・バッチ保存などの候補を個別に比較する。DB COMMIT前にACKしない境界と重複排除は維持する。
4. 本番候補の専用環境でTLS、長時間運転、障害復旧、キュー飽和、実データ量での容量・復元試験を実施する。

現時点で「MQ導入や並列化をすれば何件/秒になる」とは判断しない。MQTT Brokerは既に存在し、滞留場所を増やすだけでは持続的な保存速度は上がらない。
